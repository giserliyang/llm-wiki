## 笔记 1：进程 vs 线程 vs 协程 三层并发模型

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 13 章 进程与线程]][[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 14 章 协程]]

### 我的理解
> 用一个生活场景类比：进程像一整个餐厅，线程是餐厅里的服务员，协程是某个服务员同时照看的几张桌子。用自己的话描述这三者的资源隔离程度和切换开销差异。

### 要点
1. **进程**：OS 资源分配单位，独立内存空间，创建/销毁成本高（约 ms 级）
2. **线程**：进程内执行单元，共享进程内存，切换成本较低（约 μs 级）
3. **协程**：线程内任务调度，用户态切换，无 OS 参与，成本最低（约 ns 级）
4. **GIL 约束**：CPython 多线程无法真正并行，多进程可绕过 GIL
5. **选择策略**：CPU 密集型→多进程；IO 密集型→多线程或协程

## 笔记 2：GIL 的真相——它到底锁了什么

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 13 章 进程与线程##15. GIL 全局解释器锁]]

### 我的理解
> GIL 不是 Python 语言的约束，而是 CPython 实现的历史包袱。用自己的话解释：为什么 CPython 需要 GIL？没有 GIL 时引用计数会发生什么问题？

### 要点
1. GIL 保护的是 CPython 解释器的内部数据结构（如引用计数），不是用户代码
2. GIL 保证同一时刻只有一个线程执行 Python 字节码
3. GIL 在遇到 IO 操作（sleep、网络、文件读写）时主动释放
4. `Lock/RLock` 是业务层面的锁，与 GIL 无关，用于保护共享数据
5. 多进程可绕过 GIL：每个进程有自己的 GIL

## 笔记 3：装饰器与闭包的底层机制

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 8 章 函数进阶##12. 闭包]][[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 8 章 函数进阶##13. 装饰器]]

### 我的理解
> 装饰器本质是高阶函数 + 闭包。用自己的话描述：`@decorator` 语法糖展开后是什么？`wrapper` 函数如何"记住"外层变量？

### 要点
1. **闭包三条件**：函数嵌套 + 内层引用外层变量 + 外层返回内层
2. **cell 机制**：外层变量被封存在 `__closure__` 元组的 cell 中，不随外层函数销毁
3. **装饰器本质**：`@decorator` 等价于 `func = decorator(func)`，即高阶函数调用
4. **多层装饰器**：离函数近的先执行，顺序与书写顺序相反
5. **带参装饰器**：三层嵌套，外层收配置，中层收函数，内层收参数
6. **类装饰器**：通过 `__call__` 实现，比函数装饰器更简洁

### 疑问
> 为什么装饰器会覆盖原函数的 `__name__` 和 `__doc__`？如何用 `functools.wraps` 解决？

### 实战记录

## 笔记 4：浅拷贝 vs 深拷贝的内存模型

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 8 章 函数进阶##10. 浅拷贝 vs 深拷贝]]

### 我的理解
> 用 `id()` 函数追踪每个对象的内存地址，画出一张内存图：直接赋值、浅拷贝、深拷贝后各变量指向哪些对象？哪个变了哪个没变？

### 要点
1. **直接赋值**：两个变量指向同一个对象，修改一个另一个跟着变
2. **浅拷贝**：外层容器新建，内层元素仍是原对象的引用
3. **深拷贝**：外层容器及所有嵌套可变对象都递归复制，完全独立
4. **不可变对象**：深拷贝不会复制不可变对象（int、str、tuple 等），直接引用
5. **元组特例**：元组内只含不可变对象时，deepcopy 无效果

### 疑问
> `copy.copy()` 和 `list[:]` 哪种更快？Python 内部优化有差异吗？

### 待验证
> 用 `tracemalloc` 对比三种方式处理大数据时的内存占用

## 笔记 5：try/except 的完整执行路径

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 9 章 错误与异常]]

### 我的理解
> 画一张流程图：try 正常结束 → else 执行 → finally 执行；try 抛出异常 → 匹配 except → 未匹配则向上传递 → finally 仍执行。用自己的话描述每种情况的触发路径。

### 要点
1. **else 块**：仅在 try 无异常时执行，适合放"依赖 try 成功"的代码
2. **finally 块**：无论是否异常都执行，适合放清理逻辑（关闭文件、释放锁）
3. **异常传递**：未被当前层捕获的异常沿调用链向上回溯
4. **自定义异常**：继承 Exception，类名以 Error 结尾，增强业务语义
5. **traceback**：`e.__traceback__.tb_lineno` 可获取出错行号，`traceback.format_exc()` 格式化完整栈

### 疑问

## 笔记 6：yield / send() / yield from 的协作机制

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 11 章 迭代器 vs 生成器]]

### 我的理解
> 把生成器想象成一个可以暂停和恢复的函数。用自己的话描述：`next()` 和 `send()` 的区别是什么？第一次为什么不能 send 值？

### 要点
1. `yield` 暂停函数并返回值，下次 `next()` 从暂停处继续
2. `send(value)` 既能取值也能送值：送的值成为上一次 `yield` 表达式的结果
3. **第一次必须用 `next()` 或 `send(None)`**：因为此时没有"上一次 yield"来接收值
4. `yield from` 将可迭代对象的元素逐个 yield 出去，替代 `for + yield`
5. 生成器是特殊的迭代器，自动实现了 `__iter__` 和 `__next__`
6. `return` 在生成器中抛出 StopIteration，return 值成为异常信息

### 疑问
> `yield from` 如何传递 send 的值到子生成器？PEP 380 的设计意图是什么？

### 待验证
> 用生成器实现一个简单的状态机（如：等待输入→处理→输出→循环）

## 笔记 7：asyncio 事件循环的工作流程

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 14 章 协程]]

### 我的理解
> 事件循环就像一个调度员：管理所有注册的任务，当某个任务遇到 IO 挂起时，调度员转去执行下一个就绪任务。用自己的话描述这个调度过程。

### 要点
1. **asyncio.run()**：创建事件循环 → 包装协程为 Task → 启动循环 → 阻塞等到完成
2. **create_task()**：将协程注册到事件循环，立即开始调度，不等待
3. **gather()**：批量提交多个协程，全部完成后一次性返回所有结果
4. **await 触发切换的条件**：await 后的对象必须是可等待对象（协程/Future/Task），且内部包含 IO 操作
5. **纯计算不触发切换**：await 一个不含 IO 的协程，事件循环无法获得 CPU 控制权

### 疑问
> asyncio 是单线程的，那它如何处理 CPU 密集型任务？是否需要结合 ProcessPoolExecutor？

## 笔记 8：队列（Queue） vs 管道（Pipe）的通信模型

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 13 章 进程与线程##7-9 节]]

### 我的理解
> Queue 是多个生产者/消费者之间的共享缓冲区，Pipe 是两点之间的直接通道。用自己的话说明何时用 Queue、何时用 Pipe。

### 要点
1. **Queue**：FIFO 结构，支持多生产者多消费者，满时 put 阻塞，空时 get 阻塞
2. **Pipe**：两点之间通信，duplex=False 单向，duplex=True 双向
3. **timeout 参数**：`put(data, timeout=N)` 等待 N 秒后抛 Full 异常；`get(timeout=N)` 同理
4. **put_nowait / get_nowait**：立即操作，满/空时直接抛异常
5. Queue 天然跨进程共享，Pipe 两端分别传给不同进程

### 疑问

## 笔记 9：继承 Process/Thread 与 target 参数的两种风格

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 13 章 进程与线程##3/10/12/13 节]]

### 我的理解
> target 函数式风格适合简单任务，继承式面向对象风格适合需要状态持久化的复杂场景。用自己的话说明两种方式的适用边界。

### 要点
1. **target 方式**：`Process(target=func, args=(...))`，函数是纯逻辑，无状态
2. **继承方式**：重写 `run()` 方法，适合需要保存状态（实例属性）的复杂任务
3. 两种方式都通过 `start()` 启动，**不要手动调用 `run()`**
4. 继承 Process 时需调用 `super().__init__(**kwargs)` 传递命名等参数
5. 继承 Thread 同理，`run()` 内写逻辑，`start()` 触发执行

## 笔记 10：with 上下文管理器的完整协议

**来源：** [[raw/tutorials/python/20260919_Python教程_尚硅谷.md#第 12 章 文件操作##5. 关于with]]

### 我的理解
> `with` 的本质是"进入前做什么，退出时做什么"。用自己的话描述：为什么 `__exit__` 返回 True 就能吞掉异常？返回 False 会怎样？

### 要点
1. **`__enter__`**：with 进入前执行，返回值赋给 as 变量
2. **`__exit__(exc_type, exc_val, exc_tb)`**：with 结束时执行，无论是否正常
3. **返回 True**：异常已被处理，不向外传播
4. **返回 False / None**：异常继续向外抛出
5. `yield` 实现上下文管理器（`contextlib.contextmanager`）是更简洁的方式
6. 内置的 `open()`、`Lock`、`Queue` 等都是上下文管理器

### 疑问
